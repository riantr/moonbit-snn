# 2026-10-11 项目代码分析

## 概况
- `moonbit-snn` = SpikingNeuralNetworks.jl 的 bit-exact MoonBit 移植，但实际范围已远超"SNN 移植"，
  长成了完整 ML 栈（SNN + CNN/Transformer + LSTM/GRU + RL(PPO/SAC/DDPG) + GNN + 生成模型 + TARNet 语音）。
- 规模：mbt 根目录 499 个 .mbt，其中 207 个测试文件；examples/ 77 个示例；总文件约 1017。
- 版本 v0.165.0，已发布到 mooncakes.io（riantr/snn_mbt），CI = .github/workflows/publish.yml（tag 触发）。

## 构建状态（本次实测）
- `moon check --target native`：**0 errors, 5238 warnings**，161 tasks，约 12s。
- 警告构成：test_unqualified_package 5039（占 96%，测试文件未用限定名，可批量修）、
  deprecated 79、unused_value 64、reserved_keyword 27、其余零散。
- 工具链：moon 0.1.20260920 (914d7da 2026-09-20)。

## 关键结构发现
1. **测试三处割裂**：CI 只跑 `tests/wave1`(27文件/220用例) + `tests/wave2`(9文件/60用例) = 280 用例全绿；
   但根目录还剩 207 个 `*_test.mbt`，且 `moon test` 在根包无法链接（Windows 32K CreateProcessW 上限，
   README 已记录）。即约 85% 的测试文件不在 CI 门禁内。
2. **wave1/wave2 不是副本而是"移动"**：根目录已无 `neuron_if_test.mbt` 等文件，测试被搬到子包，
   子包通过 blackbox import 引用 `riantr/snn_mbt`。
3. **子包 import 限制**：moon 0.1.20260920 下新建子包无法解析父模块任何符号（需提交 pkg.generated.mbti，
   moon info 又依赖 import 先解析 → 死锁）。这迫使 verify/ 的 harness 靠临时把 `"is-main": true`
   写进 mbt/moon.pkg 再 `moon run .` 来执行，跑完在 finally 里还原。
4. **当前活跃工作 = TARNet 语音分离**（tarnet*.mbt 7 个文件约 3000 行），最近 25 个 commit 全是它；
   msg_decomp.md 记录了 ASP 路径 BatchNorm d_input 的未解问题（ctx 路径误差约十倍于自身量级）。
5. examples/ 有 30 个 pkg.generated.mbti 未被 git 跟踪（git status 显示 39 项未跟踪）。

## 优点
- 注释质量极高：verify_gnn_grads.ps1 / publish.yml / compose.mbt 都详述"为什么这样写、踩过什么坑"
  （如 PowerShell 变量大小写不敏感导致 $Runner 覆盖参数、bash 吞掉 403 错误）。
- 验证方法论成熟：梯度门禁用相对容差 + gradcheck_over_fraction（区分 ReLU kink 与真 bug）+ 负对照，
  历史发现 13 个类型检查和 review 都漏掉的真实缺陷（含一个符号反了的交叉熵，潜伏 6 个版本）。
- Float32 全链路 + libm FFI（expf/tanhf/logf/sqrtf/cosf/sinf/erff），bit-exact 目标明确。

## 风险 / 建议优先级
1. **高**：85% 测试文件不在 CI 门禁内 —— 建议继续按 wave 拆分把根目录测试搬进 tests/ 子包，
   或在 CI 加一个"根包测试存在性"守卫，避免新增测试默认不被执行。
2. **中**：5238 条 warning 中 5039 条是 test_unqualified_package，一次 sed 批量加 @snn_mbt. 前缀即可清零，
   收益高成本低。
3. **中**：根目录 499 个平铺 .mbt（无 src/ 分层，src/ 和 test/ 目录是空的），
   建议按 neuron/ connection/ nn/ rl/ 分目录，否则导航成本持续上升。
4. **低**：moon.mod 的 description 字段极长（数百行罗列全部特性），发布元数据可读性差，建议压缩。

## 更正与重构执行（同日续）

### 两条被实测推翻的结论（重要，勿再沿用旧判断）

1. **「MoonBit 不支持子目录组织源码」是错的。**
   我曾据 `mbt/testdata/scnn_demo_archived.mbt` 与根目录 `scnn_demo.mbt` 重复定义 3 个同名符号
   却编译通过，推断子目录被静默忽略。用户提示参考 `moonbit-community/rabbita` 后，解包其发布包验证：
   **真实机制 = 每个子目录一个子包 + 根包 `moon.pkg` 显式 `import` 子包**。
   rabbita 有 20+ 子目录、三层嵌套（`html/canvas/`），根包 import 子包、子包用 `import ... for "test"`
   反向 import 根包。**坑仍在**：无 `moon.pkg` 的目录确实被静默忽略（比报错更危险）。
   注：子包路径必须含根目录名 —— 模块 `riantr/snn_mbt` + 根目录 `mbt` → `riantr/snn_mbt/mbt/<子包>`。

2. **「拆包是安全的」也是错的。**
   探针实测：根包 `moon.pkg` 显式 import 子包后，`moon info` 生成的**根包 `.mbti` 不含子包符号**，
   即**不重导出**。源码拆出后 `@snn_mbt.IF` 对外失效 → 77 个 examples 需改写，已发布的 0.165.0
   消费者编译失败（breaking change）。`pub using` 只能重导出 **type**（且不能 `as pub X`、不能与原子包同名），
   **free fn 无法重导出**，根包有 1159 个，只能写包装函数。
   其他实测：普通双向 import 报 `Import loop detected`；`for "test"` 双向 import 允许；
   `moon.pkg` **不被子目录继承**；import 只能写在 `moon.pkg`（写进 `.mbt` 报错）。

### 工具 split_qualify.py 的四个 bug（都是编译器抓出来的，非代码审查）
1. **泛型定义不可见**：`pub fn[A] constant(A) -> Loc[A]` 中 `[A]` 让 `fn\s+(\w+)\s*[(<]` 失配，
   导致**所有泛型 free fn 从 allow-list 消失**（1159→1160）。`load_public`/`load_private`/
   `load_own_symbols` 三处正则都要加 `(?:\[[^\]]*\])?`
2. **声明行 span 边界**：span 右边界是"该行换行之后"，正好等于下一段代码段起点 →
   `sp[0] >= seg_lo` 漏判。正确做法是**遍历所有 span 切分**，且必须补回 gap
   （我第一版改对了边界却漏了 `out.append(text[decl_end:])`，导致函数体被丢弃）
3. **命名参数误改**：`cm=100.0F` 里 `cm` 既是 const 又是 struct 字段 → 被加前缀 →
   编译器读成 parameter label。用 `_named_argument_labels()` 从源头排除
   （`let x : Type = ` 这种类型标注要先掩码 `=`，但**不能掩掉类型名本身**，否则又漏改）
4. **元组解构**：`let (o2,a2,m2,h2) = ...` 中的名字像包符号，而 `m2` 真是
   `pub let m2 : Float`。`TUPLE_BIND` 必须**要求开头的括号/方括号**，否则会误抓
   `let buf : SequenceReplayBuffer = ` 把类型名也豁免掉

## 评估 moonbit_linalg_gpu 对本项目的适用性

**结论：直接用不了。三个硬阻塞，任何一个都足以否决。**

### 1. 数值类型不匹配（决定性）
`linalg_gpu` 全程 `FixedArray[Double]`（cuBLAS 只有 s/d/c/z 四精度，
d 与单精度 GPU GEMM 速度差距约 10-100 倍）。
**本项目 9769 处 `Float`(Float32) vs 97 处 `Double`——100:1。**
而且 `he_init` 明确用 N(0,√(2/fan_in)) + Float32 Box-Muller 初始化权重，
双精度累加会**改变数值结果**，与「bit-exact Julia port」的定位直接冲突。
matrix.mbt 的注释里写明调用方是 `moonbit_doubleML`——那是双精度项目。

### 2. 本项目是 SNN，不是 DL
核心负载是**动态事件驱动**：`synapse/sparse_matrix.mbt`、
`dendneuron_parameter.mbt`、`neuron_multipod.mbt`（树突多房室）。
这些是稀疏事件驱动标量循环，**GPU GEMM 无用武之地**——
没有稠密矩阵可乘，且有脉冲时刻的严格因果依赖。

### 3. 数据布局不符
matrix.mbt 全程 row-major `FixedArray`；
`nn/batch_norm2d.mbt` 是 NCHW **嵌套 `Array[Array[Float]]`**，
Conv2d 系列也是嵌套数组。跨 FFI 需要 flatten→gemm→unflatten，
拷贝成本可能吃掉全部收益。

### 真正值得借鉴的（是设计，不是代码）
1. **`#cfg` 双实现模式**（ffi.mbt:17-33）：MoonBit 在 wasm/js 后端**拒绝 extern "C"**，
   且含 FFI 的包不能被声明多后端的包依赖。
   本项目 `preferred_target = "native"` 单一后端，**当前不需要**，
   但若将来要出 wasm 版，这个模式是必需的。
2. **`#borrow` 语义**：明确 C 侧不得跨调用持有缓冲区引用。
3. **返回码分层**：`0` / `ErrLibNotLoaded(-1000)` / `ErrBadArg(-2000)` / cuBLAS 状态码，
   **库缺失与参数错误分开**——这个分层本项目也该有。
4. **原地计算不拷贝** + **行主序由 stub 内部转换**（对调用方隐藏 cuBLAS 列主序）。
5. **约定优于配置**：路径由 `MOONXI_LINALG_LIB` 环境变量 + 默认探测，
   不在线性代数 API 里传路径参数。

### 若将来真要 GPU 加速的正确做法
不是引入 `linalg_gpu`，而是：
(a) 只加速 `nn/linear.mbt` 的 `linear_forward`（当前是标量三循环，
    nn/*.mbt 只有 5 处 `for`/`while`——**热点明确但被埋在嵌套数组里**）；
(b) 需要先提供 `s`-精度的 cuBLAS wrapper（现有只有 `d`）；
(c) 在 `nn/` 下加 `gpu_linear.mbt`，CPU 实现保留为回退（沿用 -1000 哨兵）。

## 实测：linear_forward 性能（推翻了我此前的优先级判断）

写了临时基准（已清理），测 LeNet5 fc1：batch 64, 4000→500, 256 MFLOP/call。

| 条件 | reps=0 基线 | reps=20 | 净计算/次 |
|---|---|---|---|
| debug | 5.00 s | 21.77 s | 837 ms |
| **release** | 0.78 s | 1.98 s | **60.2 ms** |

**实测吞吐 4.25 GFLOP/s**，约为单核 AVX2 FMA 峰值（50–100）的 **5.3%**。

### 三个由此改变认知的事实
1. **debug 比 release 慢 14 倍**（837ms → 60ms）。此前所有 `moon check/test`
   都跑 debug，任何性能判断若基于它都会错 14 倍。
2. **`user` CPU 时间始终只有 0.02–0.2s**，而 `real` 是 2s——
   Windows 上 `time` 的 user/sys 不可信，但**必须用 reps=0 做基线相减**才能拿到真值。
3. 当前实现离单核峰值差 19 倍 → **GPU 的 3.4万–19万倍理论加速是针对峰值算力，
   而当前代码只吃到 5.3%**。真实收益 = 峰值比 × 当前效率比，需实测才知道。

### 修正我此前的排序（重要）
我上一轮说「synapse 循环密度是 nn 的 2–3 倍，所以 GPU 没用」。
**那是用 grep 循环数量得出的，不成立。**
现在有数据后：**nn 的 dense 层确实慢到值得加速**（60ms/次 一个 fc1），
而 GPU 对它的适配路径是清楚的（稠密 GEMM，正是 cuBLAS 的强项）。
SNN 事件驱动部分（synapse/stdp 等）GPU 帮不上——但那不构成放弃 nn 的理由。

**真正该先做的不是 GPU，是先确认 release 下的性能画像**：
60ms 是 release 数据；若线上跑 debug，先修构建配置收益 14 倍，零成本。

### 本轮的元教训

## 第 4 步：linear_accel 的 C stub + CUDA kernel + 构建脚本（已实测）

新增 `mbt/gpu/cuda/`：
- `linear_accel_stub.c`(365) —— TCC native-stub，dlopen 内核库，**内置 CPU 回退**
- `linear_accel_kernels.cu`(277) —— 单精度 cuBLAS 封装（唯一手写 kernel 是 fill）
- `build_linear_accel_linux.sh`(73) / `build_linear_accel_windows.ps1`(62)
- `moon.pkg` —— 声明 `native-stub` 与 `link-libraries: ["dl"]`
新增 `mbt/gpu_selftest/` + `README.md`

### 关键设计差异（相对 linalg_stub.c）
**stub 自己做 CPU 回退并返回 0**（linalg_stub 返回 -1000 让 MoonBit 侧重算）。
好处：**忘记检查返回值的调用点仍然得到正确结果**。
代价：0 只意味着「结果正确」，不意味着「GPU 算的」→ 加了 `la_last_backend()`。
cuBLAS 运行期失败也**不向上传播**，直接落回 CPU 循环——
调用者无法处理的状态码，比慢一点的正确答案更糟。

### 实测（本机无 CUDA，正好测回退路径）
```
try_load   : -1000  (库不存在，正确)
loaded     : false
sgemm out  : 58 64 | 139 154   ✓
sdot out   : 32  ✓      snrm2 out : 5  ✓
fill out   : 7 7 7    ✓      axpy out : 12 24 36 ✓
bad-arg rc : -2000   ✓
```
**C stub 真实编译、链接、执行通过，7 个原语数值全对。**

### 重要发现：FixedArray::from_array 写回不生效
第一次自测全输出 0。根因：`FixedArray::from_array` 是**视图**——
C 侧通过 FixedArray 写入的内容**不会反映到源 Array**（读可以，写不行）。
**输出缓冲区必须是真正的 `FixedArray` 值，不能是从 Array 包出来的视图。**
这写进了 gpu_selftest/README.md，因为将来接入 linear_forward 时必然再撞一次。

### 踩坑：C 宏 FOREACH 模式是错的
`LA_FOREACH_FN(X)` + `face_##name` 会生成 `face_accel_sgemm`（符号带 accel_ 前缀），
而调用点用 `LA_FN(sgemm)` → `face_sgemm` → C2039。
**宏无法从粘贴的 token 里剥掉前缀。** 改成 7 个显式声明 + 显式 lookup。
教训：**跨「符号名」与「槽位名」时，别指望宏能改名**。

### 反复犯的错误：路径拼写
`moonbit-sns`（少个 n）本轮又出现 4 次，导致文件写到错误目录、
被 rm -rf 清理掉重来。**每次 cd 前用变量或直接复制完整路径。**

## 关键测量：Array -> FixedArray 转换成本（决定 GPU 方案可行性的前置条件）

### 实测（release, 2000 次, 取最小 wall）
| | 单次 | 带宽 | 占 linear_forward(98.4ms) |
|---|---|---|---|
| input 1.0 MB | 0.426 ms | 2401 GB/s | 0.43% |
| weight 8.0 MB | 4.508 ms | 1775 GB/s | 4.58% |

### 确认 `FixedArray::from_array` 是**深拷贝**
实测：`src[0]=99` 后 `fa[0]` 仍为 1；`fa_before` 求和 8.0 而 `fa_after` 106.0。
→ **读共享内存可行，写不回流**（这解释了 gpu_selftest 第一次全输出 0）。

### 决定性结论
**转换比 PCIe 传输贵 10 倍（input）/ 110 倍（weight）。**
我上一轮说「传输占 0.04%，不是瓶颈」——**那个结论只在缓存已存在时成立**。
真实顺序是：先转换 → 再传输。没缓存就先付 0.43/4.51 ms。

**所以 GPU 方案的前置条件是：`LinearParam` 必须持有 `FixedArray`，而不是每次调用现转。**
这意味着要改 `nn/linear.mbt` 的数据结构（`Array[Float]` → `FixedArray[Float]`），
属于**侵入式变更**，收益（98.4 ms → 理论 <1 ms）能否抵偿尚未验证。

### 方法论教训（第三次栽在测量上）
1. **第一次**：reps=20，进程启动 800ms 淹没信号 → reps=0 竟比 reps=20 慢。
   修：reps 提到 2000 + 取多次采样最小值。
2. **第二次**：转换结果未被使用 → 编译器消除了拷贝 → 报出 2400 GB/s
   （超过单核内存带宽 = 明显错误）。
   修：每次转换后读一个元素累加，让工作可观测。
3. 1775 GB/s 仍不合理，说明 9016ms 里大头可能是**分配器**而非拷贝。
   **但这不影响结论——实测数字本身就是要的东西。**

**通则：任何「快得不可能」的测量结果都是 bug，不是好消息。
先质疑数字，再解释它。**

### 变异测试发现了两个真实测试缺口（这是它最大的价值）

## QA LOOP 调试：三个门禁误报的真实原因（都是我的工具，不是代码）

第一轮完整循环报 3 个失败，逐个查下来**没有一个是代码问题**：

### 1. unit 报 "wave9 失败"，实际 443/443 全绿
**根因**：`subprocess.run(text=True, errors="replace")` 把输出**截断在 406 字节**，
恰好切在 `Total tests: 220, passed: 220, faile|d: 0.` 中间 → 正则匹配不到 → 判失败。
修法：**改为二进制读取**（stdout=PIPE 不带 text），解码放到后面做。
`stress` 门禁同样受影响（把"匹配不到"当成 0 failed = 假通过）。

### 2. integration 报 "15/77 examples 失败"，实际全绿
**根因**：180 秒超时不够，首次构建慢的 example 被杀 → rc=124 → 计为失败。
修法：**区分超时与编译错误**（rc=124 或含 "timed out" → 记 timeout 不算失败），
超时提到 420 秒。收敛：15 → 8 → 1（tripod_current，三次重跑均 rc=0，并发偶发）。

### 3. dup 报 12 处，是真实技术债
`generative/energy_function.mbt` 与 `models/embedding_net.mbt` 复制了同一段 MLP 初始化。
**这个不该"修"——它是真实发现，应报告。**

### 通则（本轮最重要的一条）
**门禁误报的代价高于没有门禁。**
"15 个 example 坏了"会把人送去查不存在的 bug——而我确实花了几轮去查。
**门禁的第一职责是可信，第二职责才是灵敏。**
判据：任何门禁报的失败，**必须先单独复现确认**，再决定是修代码还是修门禁。

### 我反复犯的错
命令写成 `cd X 2>/dev/null || true; cd Y && ...` 时，
第一个路径打错（`moonbit-sns` 少个 n）会让整条命令失败。
**只用 `cd` 一次**，或依赖 shell 当前目录。

### bash 会吃掉 Python 里的正则转义
`python -c "re.search(r'\\s*\\d+')"` 里的 `\s` `\d` 会被 bash 变成 `/s` `/d`，
调试时得到"文本明明匹配却返回 None"的假象。
**测正则要写进文件再跑，或用 heredoc（`<< 'EOF'`）。**
